## 一、系统中的四类核心数据

当前系统需要明确区分以下四类内容，避免把“项目设备、视觉模型、规则库、RAG 知识库”混在一起。

```text
① 项目设备
workspace/
→ 实际项目中的 13 台设备

② 视觉模型

→ 当前实际可测试约 11 台

③ 规则库
rules/device_indicator_rules.yaml

→ 用于确定性状态判定

④ RAG 知识库
rag/device_dbs/<设备>/chroma_db
rag/global_db/chroma_db
→ 用于检索说明书、故障原因、处理方法、人工规则知识
```

runs/classify/device_cls_yolo11s/weights/best.pt

## 四、每台设备独立的指示灯检测模型

设备识别稳定之后，根据设备身份路由到该设备对应的指示灯检测模型。

```text
设备分类
↓
确认是哪台 workspace 设备
↓
indicator_model_registry.json
↓
加载该设备自己的指示灯检测模型
```

例如：

```text
数据网柜_H3C_SR6608_华三
↓
对应 H3C 指示灯检测模型
```

模型注册关系保存在：

```text
~/yolo_device_monitor/models/indicator_model_registry.json
```

系统不是使用一个通用指示灯模型识别所有设备，而是采用：

```text
设备A → detector_A
设备B → detector_B
设备C → detector_C
...
```

当前状态：

```text
项目设备总数：13 台
已有可用指示灯模型：约 11 台
2.5G、10G 两台：尚未完成标注和训练
```

## 五、指示灯标签与标注流程

**指示灯训练标签全部采用人工标注，没有使用 AI 自动标注或 AI 预标注。**

标签流程为：

```text
设备说明书 / 实际设备图片 / 视频
↓
人工确认需要标注的指示灯类别
↓
人工使用标注工具逐张框选指示灯
↓
人工填写/选择对应指示灯类别
↓
人工复核
↓
形成 indicator_annotations.json
↓
转换为 YOLO 检测数据集
↓
训练每台设备独立的指示灯检测模型
```

最终：

```text
indicator_annotations.json
```

是每台设备指示灯类别和标注框的人工确认结果。

原则：

```text
AI 不新增类别
AI 不修改类别名称
AI 不合并类别
AI 不重新编号
AI 不生成训练标签
```

指示灯检测模型的训练数据以人工标注结果为准。

## 七、指示灯状态识别层

指示灯检测模型主要负责：

```text
这是哪个指示灯
指示灯在哪里
```

但状态引擎真正需要的是：

```json
{
  "indicator": "业务板 STAT 状态灯",
  "color": "red",
  "state": "on"
}
```

因此指示灯检测之后，还需要状态识别层：

```text
指示灯 bbox
↓
颜色判断
↓
亮 / 灭判断
↓
连续帧时间分析
↓
常亮 / 闪烁判断
↓
结构化 observation
```

最终形成：

```json
{
  "device": "H3C SR6608 路由器 AR02",
  "observations": [
    {
      "indicator": "业务板 STAT 状态灯",
      "color": "red",
      "state": "on"
    }
  ]
}
```

然后提交给：

```text
POST /judge
```

当前前端中的颜色和状态仍可手工填写，用于联调状态引擎。

## 八、确定性规则库

真正负责以下判断的是规则库：

```text
正常？
异常？
warning？
critical？
是否正式报警？
```

规则分为两类：

```text
rules/
├── device_indicator_rules.yaml
└── custom_device_rules.yaml
```

### 8.1 基础规则库

文件：

```text
rules/device_indicator_rules.yaml
```

基础规则应该来自：

```text
设备说明书
巡检总表
人工确认的厂家状态定义
```

例如说明书明确写：

```text
业务板 STAT 状态灯
红灯亮 → 单板硬件故障
```

可以转换为：

```yaml
color: red
state: on
meaning: 单板硬件故障
severity: critical
alarm: true
```

### 8.2 自定义规则库

文件：

```text
rules/custom_device_rules.yaml
```

用于保存现场人工新增或修正的规则。

例如说明书没有定义：

```text
ACT 黄色常亮
```

但现场人工确认：

```text
黄色常亮 = 业务板状态异常
```

则应该写入：

```text
custom_device_rules.yaml
```

而不是伪装成说明书规则。

运行时规则优先级：

```text
base rules
+
custom rules
↓
custom rules 优先
```

## 十、设备名称映射

视觉识别输出的 workspace 名称和规则库名称可能不同。

例如：

```text
workspace：
数据网柜_H3C_SR6608_华三

规则设备：
H3C SR6608 路由器 AR02
```

因此需要：

```text
rules/device_alias_map.yaml
```

进行映射：

```text
workspace 设备名
↓
canonical device
↓
rule device
↓
对应设备知识库
```

已经验证成功的例子：

```text
数据网柜_H3C_SR6608_华三
↓
H3C SR6608 路由器 AR02
```

项目原则：

```text
设备身份是否已确认
≠
设备是否已经有基础规则
```

即使某台 workspace 设备暂时没有基础规则，只要它是项目真实设备，也应该被认定为已验证设备。

## 十三、规则库与 RAG 的职责边界

必须保持：

```text
规则库
→ 决定是否报警

RAG
→ 提供解释、说明书证据、原因、处理方法
```

确定性规则命中：

```text
warning / critical
↓
正式 alarm = true
```

如果只有 LLM / RAG 推断异常：

```text
不能正式报警
↓
alarm = false
needs_review = true
```

即：

```text
LLM 不能推翻确定性规则
LLM 不能独立创建正式故障报警
```

```text

≠

```

例如人工规则：

```text

```

只能进入：

```text

```

```text

```

## 十五、说明书证据校验机制

说明书证据需要经过多层保护。

### 15.1 原文引用校验

每条说明书证据必须提供：

```text
source_index
+
quote
```

并且程序验证：

```text
quote 必须真实存在于对应 RAG chunk
```

### 15.2 故障场景锚点

必须先确认说明书明确描述了当前异常状态。

例如：

```text
业务板 STAT 状态灯
红灯亮 → 单板硬件故障
```

说明书明确存在，因此：

```text
manual_evidence_found = true
```

而：

```text
业务板 ACT 激活灯
黄色常亮
```

说明书没有对应定义，因此：

```text
manual_evidence_found = false
```

即使说明书其它位置出现：

```text
业务板硬件故障
拔插业务板
```

也不能强行作为 ACT 黄色常亮的处理方法。

### 15.3 程序级锚点兜底

为了避免 LLM 漏判说明书中已经明确存在的状态，当前还增加了程序级局部窗口匹配：

```text
indicator
+
color
+
state
+
meaning
```

在同一局部说明书窗口满足时，可以建立直接异常锚点。

## 十八、人工规则进入知识库后的处理

人工规则进入设备独立知识库时标记为：

```text
source_type = custom_rule
```

厂家说明书标记为：

```text
source_type = manual
```

因此后续 RAG 可以同时检索：

```text
厂家说明书
+
现场人工规则
```

但是系统仍严格区分：

```text
manual evidence
≠
custom rule evidence
```

人工规则不会冒充说明书证据。

## 十九、当前最重要的待完成工作：重建 13 台设备基础规则库

当前视觉模型和 RAG 基本已经完成，但：

```text
rules/device_indicator_rules.yaml
```

仍然主要继承了历史 24 台规则设备体系。

这会导致：

```text
项目只有 13 台设备
规则资源却有 24 台

某些设备已有 RAG
但没有对应 base rule
```

因此下一阶段应重新构建以 13 个 workspace 为核心的基础规则库。

推荐流程：

```text
13 个 workspace
↓
读取说明书结构化信息
↓
读取巡检总表
↓
必要时回查原始说明书 / 当前设备 RAG
↓
提取明确的规则候选
↓
人工审核
↓
形成新的 device_indicator_rules.yaml
```

规则来源原则：

```text
说明书明确写出的状态
→ 基础规则候选

说明书不明确
→ 不自动生成确定性规则

现场人工确认
→ custom_device_rules.yaml
```

例如：

```text

```

适合进入基础规则。

而：

```text
ACT 黄色常亮 → 异常
```

如果只有现场人工确认，则保留在 custom rule。
